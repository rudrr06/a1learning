What just happened?

The step you are on lights up here.

  1. 1. Normal input – The app glues whatever the user typed straight into a SQL string. With normal text this works fine.
  2. 2. Normal result – The database finds one matching row (username and password match) and logs the user in.
  3. 3. Malicious input – The attacker types admin' -- . The ' closes the text value early, and -- starts a comment (in MySQL it needs a space after it). Their input is now part of the code.
  4. 4. The bypass – Everything after -- is ignored, including AND password = .... The database only checks the username, so the attacker is in as admin without knowing the password.
  5. 5. The fix – With a parameterized (prepared) query, the SQL and the values travel separately. The database treats the input as plain text only, so the trick does nothing.

Why does security care?

Login bypass is the gentle version. The same flaw can let attackers read other tables, change data or delete it. Injection has been among the most serious web risks for years.

Defenses: parameterized queries (the main fix), least-privilege database accounts, server-side input validation, and using an ORM correctly.

Only practice on systems you own or on safe training labs such as DVWA or the PortSwigger Web Security Academy.
