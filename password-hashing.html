Password Hashing

Why websites never store your real password, and how weak storage still gets cracked. The hashes below are real SHA-256 values.

Try it yourself

Type anything. Then change just one letter and watch the whole hash change.

SHA-256 always gives 64 hex characters (256 bits), whatever the input length.

What just happened?

The step you are on lights up here.

  1. 1. Plain text – The worst option: passwords are stored exactly as typed.
  2. 2. Breach – If the database leaks, every password is readable immediately.
  3. 3. Hashing – A hash is a one-way fingerprint of the password. It cannot be reversed directly, but the same password always gives the same hash, so alice and bob match.
  4. 4. Dictionary attack – The attacker hashes a list of common passwords and compares. Weak passwords are found instantly. Strong, unique ones survive.
  5. 5. Salting – A random salt is added before hashing, so identical passwords produce different hashes and precomputed tables stop working. The salt is stored next to the hash and is not secret.
  6. 6. Slow hashing – Argon2, bcrypt or scrypt are deliberately slow, which makes every guess expensive for the attacker.

Why does security care?

Real breaches have shown that unsalted, fast hashes get cracked quickly (LinkedIn's 2012 breach is a well-known example). A fast general-purpose hash like SHA-256 is fine for fingerprints, but not for storing passwords.

Hashing is not encryption: encryption can be undone with a key, hashing cannot. If a site can email you your original password, it stored it in a recoverable form, which is a bad sign.
